# 社区食堂助餐覆盖率换版复核

`hxwl-solo2611-10` · 指标口径与版本复算

社区台账员汇总户籍、常住及助餐需求名单，各食堂上报结算单。数据组用同一批名单快照和结算单重算新旧两版覆盖率，逐笔解释资格变化带来的差值，再决定新版数据能否进入月报。

## 模拟客户与工作流

榆棠区民政局养老服务科数据组 · 4 名复核员，负责 3 个社区的助餐月报

- 不同食堂各自去重，跨食堂用餐的居民在区级汇总时被重复计入。
- 旧版户籍名单和新版常住名单分别导出，月报只能看到分母总数，查不到谁进了谁出去了。
- 社区覆盖率直接取平均，小社区和大社区对区级结果的影响一样大。

养老服务科负责人依据换版差值和资格变动明细签署复核意见。达标结果可交区民政月报编审组，超差或缺分母时由街道助餐台账组核对名单后重新试算。

## 业务模块

- 名单与餐单
- 双口径试算
- 覆盖率与归因
- 月报分发

## 计算口径

旧版分母为本区户籍在册且年满 65 周岁的居民。新版分母为本区常住且年满 65 周岁的居民，以及 60 至 64 周岁、已评估有助餐需求的本区常住居民。批次使用单一冻结名单，换统计窗口只筛选餐单，用餐按名单所属社区归集。先按结算流水号归并：完全相同的重复上报只算一条；同一流水出现内容不同的补报且都成立时视为一组补报冲突，每组只选一条实报，新旧两版共用同一组餐单，因此必须联合求解。保留期内完成的餐单，再对有名单的居民跨食堂去重，并按各版资格分别计入分子。撤销、试餐及名单外餐单进入核销明细。区级率以各社区分母为权重，即分子合计除以分母合计。归因以旧版区级率为基准，每类资格变化的贡献为（分子变化 − 旧版率 × 分母变化）÷ 新版分母。对全部可行补报组合逐一试算，给出新版减旧版差值的最小与最大百分点，并可查到达到两端的餐单；只有整个范围都落在月报门槛内（含等于）才可分发。任一版区级分母为零时暂停分发。

补报并入原批次，源数据更新后旧试算的分发资格即失效。同批并发试算只认最后受理的一次，算完才可分发。已发月报按当时存档的餐单组合复算，不受后续改单影响。

样例输入为 `榆棠区助餐换版复核_2026-11.csv`，见 `backend/demo/sample.csv`。相同输入与参数复现相同结果。格式错误在导入时提示，样本量或业务约束不满足时在后台运行结果中提示。

## 补报撞流水与可行范围

同一结算流水号若被补报成两条内容不同的餐单，导入时不再直接报错，而是记为一组“补报冲突”。试算会遍历所有“每组选一条”的可行组合，在页面给出换版差值的最小与最大百分点，并在“两端所选补报餐单”表列出达到两端时各流水分别选了哪条。月报门槛按整个范围判定：最小值不低于负门槛且最大值不高于正门槛才可分发。参考组合仍按“完成优先、日期最早”稳定选取，用于生成归因与明细。

批次按名称形成版本链：再次导入同名批次即追加新版本并置为当前，旧版本保留。未分发的旧试算在当前版本变化后显示“资格失效”。同批并发试算通过批次行锁串行受理，后受理者使先前的未分发试算变为“已被覆盖”，只有最后受理且算完的一次可分发。已经投递的月报会把当时的餐单组合存档；需要复核时用“按存档复算”在原批次上复现当时结果。

## 一班如何使用

1. 11 月 24 日 08:40，台账员导入榆棠区助餐换版复核_2026-11.csv，核对 11 月 23 日冻结的 22 名居民和 3 个社区的食堂结算记录。
2. 09:00，分析员按 11 月 1 日至 23 日试算，核对 M002、M018 的完全重复上报与 M029 的补报撞流水，以及 R001、R009、R015 的重复用餐。
3. 09:20，核销员检查撤销、试餐、名单外及窗口外餐单，确认跨社区用餐回归名单所属社区。
4. 10:00，数据组核对旧版 8/14、新版 9/16，并从资格变动明细复查退出和新增居民，在“两端所选补报餐单”核对换版差值两端的补报选择。
5. 10:20，负责人把允许换版偏差改为 0.5 个百分点重跑，确认 0.8929 个百分点的绝对差值会暂缓分发。
6. 11:00，负责人回到 1 个百分点的月报门槛保存复核意见，确认整个补报差值范围都在门槛内后，由定时分发将达标结果送入区民政月报编审组收件箱。

## 启动与本地开发

```sh
cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

停止本地服务可执行 `docker compose down`。仅清理演示数据时使用 `docker compose down -v --remove-orphans`。

浏览器 `http://127.0.0.1:18319`，API `http://127.0.0.1:19319`，数据库宿主端口 `17819`。

前端由 Nginx 提供原生 HTML/CSS/JS，并将 `/api/` 转发给 FastAPI。Python 3.11 Worker 使用 Redis 唤醒和 MySQL 8.0 运行租约，生成的 CSV 由命名卷共享。可编辑 `frontend/src/pages`、`backend/src/services/analysis.py` 和 `backend/demo` 后执行 `docker compose up -d --build --wait`。Compose 默认映射到本机回环地址。更改 `.env` 可配置端口、数据库密码、JWT 密钥以及 `SEED_DEMO` 种子开关。演示凭据适用于本机模拟数据。

| 角色 | 账号 | 密码 | 工作内容 |
|---|---|---|---|
| 主管 | admin | admin-demo-2611 | 查看审计，复核运行，安排与停用分发计划 |
| 分析员 | analyst | analyst-demo-2611 | 导入 CSV、运行计算、下载结果 |
| 只读 | viewer | viewer-demo-2611 | 查看数据、结果和投递回执，下载 CSV |

角色、运行状态和复核状态在 `backend/src/constants/enums.py` 与 `frontend/src/constants/enums.js` 同步定义。角色参与登录、路由授权和工具栏控制。运行状态在 Worker、任务接口和结果页使用。复核状态在运行模型、复核接口和交付页使用。

核心实体为 CSV 数据批次、分析运行、分发计划及其投递回执。业务参数与真实模拟数据位于 `backend/demo/`。后端分为 routes、controllers、services、models、schemas 和中间件，前端分为 api、store、组件和业务页面。授权模式见 [LICENSE](LICENSE)。
